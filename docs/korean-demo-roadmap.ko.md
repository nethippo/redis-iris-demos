# 한국 고객용 Redis Iris 데모 개선 계획

작성: 2026-10-08 · 문서 정리: 2026-10-12

Radish Bank를 한국어 업무 조회, 정책 근거, 의미 기반 캐시, 세션 간 개인화를 설명할 수 있는 데모로 개선한다. Sports Desk는 공통 코드 회귀 확인 대상이며, 공통 실행 근거 표시 개선을 함께 적용한다.

## 현재 상태

- 한국어 Guardrail 개선은 구현됐다. 이 로드맵은 그 이후의 작업이다.
- 자동 장기 기억의 사전 검증을 수행했다. 애플리케이션의 자동 기억 통합 개선은 아직 구현·배포하지 않았다.
- **장기 메모리 최대 30일 자동 만료는 요구사항이며, 현재 적용된 기능이 아니다.**
- 다음 구현 단계는 변경 범위, 서비스 쓰기 범위, 검증 기준, 배포 대상을 제시하고 단계별 승인을 받은 뒤 진행한다.
- 이 문서는 운영 설정이나 전체 제품 품질을 보증하지 않는다. 실행 로그, 계정 설정, 서비스 식별자, 측정 원본은 Git 제외 경로 `output/`에 별도 보관한다.

## 1단계: 자동 기억과 최대 30일 보존

### 1-A. 사전 검증에서 확인한 통합 과제

“기억해줘”라는 명령 없이 세션 대화에서 장기 기억이 자동 추출되는 경로를 확인했다. 최초 추출, 선호 변경, 사용자·namespace 구분, 이전 대화 없이 검색한 기억으로 응답하는 과정을 각각 검증했다. 이 진단을 현재 브라우저 채팅의 전체 기능 완료로 간주하지 않는다.

현재 코드에서 해결할 부분:

1. `MemoryService.add_session_event()`는 namespace와 인자로 받은 metadata를 요청 본문에 전달하지 않는다. 반면 장기 검색은 ownerId와 namespace를 함께 필터링한다. 따라서 namespace 없이 추출된 기억은 도메인별 검색에서 제외될 수 있다.
2. 일반 에이전트 경로는 사용자 질문과 최종 답변을 기록하지만, 캐시 적중·Guardrail 종료는 기록 전에 반환한다. Simple RAG도 같은 기록 경로를 사용하지 않는다.
3. 한국어 대화의 추출 언어와 한국어 검색 품질을 별도로 검증해야 한다. 자동 추출 성공은 현재 검색 임계값에서의 한국어 회상 성공을 뜻하지 않는다.
4. 명시적 `remember_customer_detail` 도구는 아직 실제 저장을 수행하지 않는 데모 응답을 반환한다. 프롬프트와 화면은 저장되지 않은 정보를 저장했다고 안내하면 안 된다.
5. 저장, 추출, 검색, 회상은 별도 단계이다. UI는 각각의 성공·대기·실패를 실제 관측 범위 안에서 표시해야 한다.

### 1-B. 구현 예정 범위

- 신규 세션의 첫 이벤트에 서버가 결정한 도메인 namespace를 전달한다. 기존 세션이나 namespace 없는 기억을 일괄 재분류하지 않는다.
- 모든 대화 경로의 기록을 정리하고, 원문 보관과 개인화에 사용할 정보 추출을 구분한다. 업무 외·차단 기록을 고객 선호로 사용하지 않는다.
- 재시도에 따른 중복 기록과 저장 실패의 재처리를 설계한다.
- 한국어 추출 유지 또는 검색어 정규화 등 대안을 검증한다. 진단용으로 낮춘 검색 임계값을 그대로 운영 기본값으로 사용하지 않는다.
- 계좌 잔액·금리 같은 시점 의존 정보는 현재 데이터에서 다시 조회한다. 과거 대화나 모델의 제안을 고객의 현재 사실·선택으로 간주하지 않는다.
- 새 세션에서 관련 기억을 검색하고 한국어로 회상하는 경로를 검증한다.

### 30일 만료 요구사항

- 목표 상한은 최초 기억 생성 후 **30일(2,592,000초)**이다. 조회나 기억 갱신으로 이 상한이 계속 연장되지 않도록 한다.
- 저장소에서 실제로 만료돼야 한다. 오래된 기억을 검색에서 숨기는 것만으로 완료 처리하지 않는다.
- 서비스 TTL의 기준이 생성 시각인지 갱신 시각인지 확인한다. 고정된 최대 보존 기간을 단순 TTL 설정과 같은 의미로 취급하지 않는다.
- 요약과 원문에서 만료된 기억이 다시 생성되는 경로도 검토한다. 전체 원문 보관을 추가한다면 그 보존·추출 정책을 함께 정한다.
- 서비스 전체 설정 변경 전 다른 데모와의 공유 범위 및 기존 기억에 대한 영향을 확인한다. Radish만 적용할지 서비스 전체에 적용할지 결정한 뒤 변경한다.
- 서비스 단위 TTL로 범위를 충족할 수 없다면 데모 전용 보존 설계의 운영 영향과 복구 방법을 별도로 제시한다.
- 적용 후 실제 TTL·만료 시각을 확인한다. 짧은 TTL 소멸 시험은 테스트 전용 자원에서 가능한 경우에만 수행한다. 설정 확인을 실제 30일 경과 시험으로 보고하지 않는다.

### 완료 기준

- 한국어 합성 선호가 명시적 저장 명령 없이 자동 추출되고 새 세션에서 올바르게 회상된다.
- 선호 변경이 반영되고 다른 owner/namespace의 기억이 섞이지 않는다.
- 실패를 저장 완료나 회상 성공으로 표시하지 않는다.
- 승인된 데이터 범위에 30일 자동 만료가 적용되고 갱신·재추출 조건까지 검증된다.
- Radish 조회·정책 질문과 Sports 기존 흐름 회귀를 확인한 뒤 승인 범위의 Docker 컨테이너를 배포한다.

## 후속 단계

각 단계는 직전 결과를 반영한 구체적인 범위를 승인받은 뒤 시작한다. 아래 수치는 향후 합격 목표이며 달성한 결과가 아니다.

| 단계 | 변경 범위 | 완료 기준 |
|---|---|---|
| 2. 한국어 LangCache | 공개 예금 FAQ의 한국어·영어·혼합 표현 지원, 개인·거래 질문 제외, 언어·정책 버전별 캐시 관리 | 별도 공개 FAQ 20개 이상에서 올바른 응답 적중률 90% 이상. 개인·거래·혼합 요청 20개 이상에서 부적절한 캐시 응답 0건. 구버전·다른 도메인 응답 제외 |
| 3. 후속 대화 | 최근 대화와 업무 상태를 사용해 “그 계좌는?”, “네” 등을 처리. 미분류·업무 외·서비스 오류 구분 | 다회차 시나리오 30개 이상에서 정상 후속 질문의 기대 경로 도달률 95% 이상. 업무 외 오허용·다른 사용자 맥락 사용·모호한 확인에 의한 거래 실행 0건 |
| 4. 한국어 화면·은행 데이터 | 시작 질문·안내·상태 문구와 가상 고객·지점·원화 상품·정책 문서 현지화 | 데이터 필드·모델·도구 입력·계산·캐시 사이의 통화 및 상품 조건 일치. 가상 시연용 표시와 정책 버전/기준일 제공 |
| 5. 실행 근거·성능 비교 | 업무 조회·메모리·캐시·라우팅 표시 구분, 문서 근거, 캐시 전후 시간·모델 호출 비교 | 표시와 실제 요청 이벤트 일치. 동등한 조건의 합성 요청 10쌍 이상 비교. 채팅 모델과 임베딩 호출을 구분하고 사전 절감률을 약속하지 않음 |
| 6. 통합 리허설 | 5분 업무 담당자용 및 15분 기술 담당자용 대본, 사전 점검·정리·복구 안내 | 핵심 한국어 시나리오 10개를 각각 3회 확인. 재시작 후 대표 조회·회상 검증. Sports 회귀와 도메인 격리 확인 |

거래 관련 시험은 격리된 합성 데이터나 모킹을 사용한다. 새 실제 금융 기능을 추가하지 않는다. 한국어 라우팅 평가를 답변 정확도 전체의 평가로 표현하지 않는다.

## 공유 서비스 보존과 배포

- 기존 키와 외부 Redis 연결을 유지하고 비밀정보를 커밋하지 않는다.
- 공유 Redis·LangCache·Agent Memory의 전체 flush나 전체 데이터 재적재를 하지 않는다.
- 테스트 owner, namespace, 생성 ID를 기록하고 이번 테스트가 만든 자원만 정리한다.
- Radish는 기존 3041/8041, Sports는 3040/8040 포트를 유지한다.
- 배포 전 이미지 ID와 변경 대상 데이터 범위를 기록한다. 이미지 복구와 데이터 복구를 구분한다.
- 공통 UI 변경 단계는 두 데모를 검증한다. Radish 전용 변경은 Sports의 이미지·데이터·설정을 보존한다.
- 단계별 결과를 보고하고 다음 단계 승인을 기다린다. commit/push도 별도의 명시적 승인 범위에서 수행한다.

## 관측 범위와 별도 과제

Data Flow의 RDI 경로는 실제 연결된 CDC 서비스의 관측값이 아니라 설명용이다. 관리형 API 호출 시간과 내부 Redis 명령 실행 시간을 구분한다.

실제 Source DB/RDI 구축, 실제 사용자 인증·행 단위 권한, 금융 거래 연동, Sports 전체 콘텐츠 현지화, 새로운 외부 서비스 도입은 별도 범위로 계획한다.
